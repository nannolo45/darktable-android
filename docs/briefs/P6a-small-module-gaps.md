# Brief P6a: small module gaps from the audit (white balance presets, graduated density position, pickers and auto buttons)

Branch `p6a-small-module-gaps` from `main`. Read CLAUDE.md, PLAN.md 6.1, `docs/experiments/P5a-module-audit.md` (the rows named below) and the P3c report (`docs/experiments/P3c-colour-pickers-REPORT.md`, how pickers already work end to end). The owner chose these as the first audit items (26 Nov 2026). Read each module's manual page before building its part (CLAUDE.md rule 8).

Three items, in this order; each complete and tested before the next.

1. **White balance "settings" list** (`temperature`). Desktop's list of the camera's presets (daylight, cloudy, shade, flash, …, plus "as shot", "camera reference", "user modified") and the fine-tuning slider that appears for presets that have fine-tuning, as on desktop. The bridge already has `module_action temperature list_presets / apply_preset` (C14); extend it for fine-tuning if needed. The list shows only what the photo's camera has (wb_presets.json in the APK). One history item per choice. Tests: bridge (a preset and a fine-tuning step on the test cameras give desktop's temperature/tint and coefficients; darktable-cli parity of the written XMP), JVM, screenshot in the three skins.
2. **Graduated density: position of the filter line** (`graduatednd`, parameter `offset`). Desktop sets it only by dragging the line on the photo. Build a slider through a schema override (range and step as the parameter's introspection gives). If the existing on-photo frameworks (crop P3a, perspective P3n) make an on-photo line with its two handles (move = offset, turn = rotation) small, build that too and say so; otherwise leave it for later and say so. Tests: override loads; a slider change gives the same picture as darktable-cli with the same offset in the XMP.
3. **Missing pickers and "auto" buttons**, one package, in this order of usefulness: rgb levels "auto" and "apply auto levels from an area"; AgX's five pickers and three buttons; colour equalizer's two pickers; colour zones "create a curve from an area"; colour harmonizer's hue pickers and "analyze"; split-toning and colorize hue pickers; spektrafilm's two pickers; unbreak input profile's pickers and "auto tune level"; basic adjustments "auto" and pickers; fill light's picker; color balance's two pickers; invert's film colour picker (makes invert usable); levels' auto and pickers. Do **not** take on negadoctor, the colour checker of color calibration or anything that needs a new on-photo tool or graph editor. Each picker and button must give the parameters desktop's own code gives for the same area (desktop's `color_picker_apply` / button callbacks), by the same route P3c chose (say which route per module). If one of them turns out large (for example needs desktop GUI state the bridge cannot provide), stop on that one, list it in the report with the reason, and go on with the next. Tests: per module a bridge test against desktop's formula or code for a fixed area on a test RAW (the `pickref` approach of P3c where desktop's code cannot be called), JVM tests for the app side, and one emulator scenario that picks with rgb levels "auto" and with one AgX picker by taps (follow `P5cTapTest`; close the keyboard after a module search).

After all three: re-run `tools/module-audit.py` after updating the audit's verdict table in the script for what changed, and commit the changed `modules.json` and `P5a-module-audit.md` (works / partly counts move).
