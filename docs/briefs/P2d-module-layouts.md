# Brief P2d: module layouts as in darktable

Phase 2. Read `CLAUDE.md` (rule 8 is why this brief exists), `docs/PLAN.md` section 3.9, `docs/design/ui-spec.md`, the P2a report and write-up, and in the darktable user manual the pages "module groups", "quick access panel" and "manage module layouts" (darkroom → organization) and "white balance" and "color calibration" (module reference). The implementation of record is upstream's `src/libs/modulegroups.c` at the pinned commit.

## Why
The owner arranges darktable on the desktop the way he works: his own module groups and his own quick access panel. The interface preview shipped with groups taken from each module's default group and a quick panel invented for the preview (it offered white balance temperature, which the manual says to leave alone in the scene-referred workflow). The app must instead carry darktable's layouts: the same defaults, the same things to configure, and a layout made on the desktop must be usable on the phone.

## Deliverables
1. **Layout model** (pure Kotlin, in `schema` or a new small module): darktable's layout preset as data: options (search shown, what the active group shows), quick access on or off with its list of controls, groups with name, icon name and modules. Parse and write the exact string darktable stores (see `_preset_to_string` / `_preset_from_string` and the syntax comment in `modulegroups.c`). Round trip is byte-exact for every built-in layout.
2. **Built-in layouts from upstream, by a repeatable tool**: a script under `tools/` that produces a data file with darktable's built-in layouts ("workflow: scene-referred", "workflow: display-referred", "workflow: beginner", "modules: all", "search only", the deprecated one) for the tone mappers upstream distinguishes, at the pinned upstream commit, and records that commit in the file. How is your choice (for example reading them out of a darktable run on Linux, or from the source), but it must be rerunnable at the next upstream bump and must fail loudly when upstream's structure changes. No hand-typed module lists. The app's default layout is "workflow: scene-referred".
3. **Darkroom uses the current layout**: group tabs, the modules in each group and the quick panel all come from it. Quick access entries are darktable's control paths (`exposure/exposure`, `channelmixerrgb/temperature`, `agx/curve/contrast`): map them to controls of the schema; an entry that cannot be mapped yet is shown disabled with its name, never dropped, and listed in the report. The "active" group and deprecated modules behave as the manual describes. If a layout shows search, the module list has a search field that finds modules by name, as on desktop.
4. **Layout editor** for phone and tablet, following the manual's "manage module layouts": choose the current layout; new, duplicate, rename, delete (built-in ones cannot be changed or deleted, only duplicated); per layout: add, rename, remove and reorder groups, add and remove modules in a group, switch quick access on or off, add, remove and reorder its controls, the two options. Reached from the group tabs' row, as the presets menu sits next to the tabs on desktop.
5. **Bringing a layout in and out**: import a layout exported from desktop darktable and export one for it. First establish from upstream's source what desktop darktable actually offers for layout presets (the `.dtpreset` export and import in preferences → presets, `common/presets.c`; the format of `op_params` for the `modulegroups` operation) and write it down. Import and export files in that format through Android's file picker. If desktop cannot export layout presets as files, say so plainly and propose the smallest alternative; do not invent a format.
6. **Storage behind an interface**: a `LayoutStore` interface (list, read, write, delete, current) in `engine-api`, with an app-private file implementation now. Later the real engine keeps layouts in darktable's own database (`docs/design/engine-api.md` section 3); design the interface so that swap changes nothing in the screens.
7. **White balance as the manual describes**: nothing invented for it. It follows from 2 and 3 that the default quick panel carries color calibration's controls and no white balance control. Note in the report what else desktop does around these two modules (the warnings it shows) that needs engine support, as a follow-up; do not fake it.
8. **Tests**: unit tests for parse and write (all built-in layouts, hostile and truncated strings, unknown module names kept), for mapping quick access paths to schema controls (report the full table: mapped, not mapped), for the store; screenshot tests for the default layout on phone and tablet, the quick panel, the editor's main screens, and one imported layout. The existing tests keep passing; where a test encoded the old invented quick panel, change the expectation to the new truth and say so.
9. **CI and preview**: the app workflow keeps publishing the interface preview APK; say in the owner instructions what is new and how to bring a desktop layout to the phone, step by step.

## Limits
- Screens stay within `CLAUDE.md` rule 5 (tokens and icons only). New icons and tokens go into `ui-icons` and `ui-theme` the established way.
- No changes under `engine/`, `deps/`, `upstream/`, `app/lpl-shell`, `app/engine-jni`, `app/g0`. `schema/ui-schema.json` is not edited by hand; if the extractor must change to deliver item 2, change the extractor and regenerate, and say what else changed in the generated file.
- Presets and styles are not part of this brief (they need engine calls first).
- No person's name, device model, real file from anyone's computer or private link anywhere. Example layouts in tests are made up.
- Branch `p2d-module-layouts`, do not merge.

## Acceptance
- Byte-exact round trip of every built-in layout; the tool reruns cleanly from a clean checkout as documented.
- With the default layout, the darkroom's groups and quick panel equal desktop darktable's for the scene-referred workflow at the pinned commit (show the comparison in the report).
- A layout edited in the app, exported, and imported again is identical.
- CI green on the last code commit, or failures explained first in the report.
