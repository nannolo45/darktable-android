# Brief P4a: robustness (PLAN.md 6, Phase 4: interrupted downloads and syncs, low memory, local crash log)

Branch `p4a-robustness` from `main`. Read CLAUDE.md, PLAN.md 4.1 (agent client, jobs, heartbeat) and 6, the reports of P2e (LPL client), P2k (batches), P3k (background sync: SyncService, SyncJob) and T1. The owner approved working through Phase 4 overnight (25 Nov 2026) before his gate G3 phone check. Target phone: Snapdragon 865, 12 GB RAM, Android 13 (ColorOS).

## Deliverables
1. **Resumable downloads.** A RAW download cut by a lost connection, the app being killed, or the phone sleeping resumes where it stopped instead of starting again: keep a partial file, resume with an HTTP `Range` request, check the result (size and, where LPL gives one, checksum) before it is used; never open a partial file in the engine. Check whether LPL's `GET /api/photos/{id}/original` answers `Range` (plan row R4): read the LPL repository at /home/claude/lpl (read-only for you, branch main) and test against a locally started LPL server as P3l's interop test did. If LPL does not support it, the app falls back to a full download and the report says what LPL must change (do not change LPL).
2. **Interrupted syncs.** Every upload (XMP, preview, export, shared items) is safe to repeat after an interruption: retried with backoff, never duplicated on the server, never reported `done` before the server confirmed. A process killed mid-upload resumes the work on the next start or by the P3k service. Show the state honestly in the existing sync bar ("waiting for connection", "retrying").
3. **Low memory.** Handle `onTrimMemory`/`onLowMemory`: drop the engine's caches and thumbnails as far as needed, keep the open edit. A render that runs out of memory fails gracefully (message, edit kept, app alive), never a crash. Measure what the engine holds in memory on the emulator (label x86_64) and say what the phone numbers will need.
4. **Local crash log.** Kotlin uncaught exceptions are written to a log file in the app's own storage before the process dies; native crashes and ANRs are read on the next start from Android's `ApplicationExitInfo` (API 30+) and added to the same log; bridge errors that the app shows are logged too. Size-capped (e.g. last 200 entries / 1 MB). Settings › About gets "crash log" with the entries, "copy" and "clear". Nothing is sent anywhere. No personal data beyond what the app already stores (no photo content).
5. **Tests:** downloads cut at random points and resumed (JVM against a fake server that honours `Range`, and one emulator scenario that kills the transfer); uploads repeated after an interruption leave one result on the server (fake server and, if quick, the real LPL); onTrimMemory levels drop caches and keep the edit; an uncaught exception and a simulated exit record end up in the log; screenshot of the crash log screen in three skins.
